# SEO + AEO Growth Agent
## Production Architecture and Technical Design

**Document status:** Draft — Open for architecture review  
**Version:** 0.1  
**Primary language:** Python  
**Orchestration:** LangGraph  
**Relational database:** PostgreSQL  
**Vector database:** ChromaDB  
**Cache and coordination:** Redis  

---

# 1. Executive Summary

## 1.1 Purpose

Build an autonomous, continuously operating SEO and Answer Engine Optimization (AEO) system that helps a website improve organic search traffic, content relevance, technical health, and visibility in AI-generated answers.

The system should require only a website domain as its initial input. It should discover public pages, collect available data, evaluate website performance, identify keyword opportunities, recommend content improvements, track results over time, and generate consolidated reports.

The system must distinguish between:

- Observed facts retrieved from authoritative data sources.
- Findings derived from deterministic analysis.
- Recommendations generated by an LLM.
- Predictions about potential traffic or visibility improvements.
- Actual outcomes measured after changes are implemented.

It must not claim that a recommendation caused traffic growth without adequate evidence.

## 1.2 Primary objectives

1. **Automated website auditing:** Discover pages and identify technical SEO, performance, crawlability, and AEO readiness issues.
2. **Keyword and trend intelligence:** Identify keywords that already perform well, opportunities to improve existing pages, and relevant emerging topics.
3. **Content strategy:** Recommend which pages to optimize and which new content to create.
4. **Continuous monitoring:** Track SEO metrics, selected AI-answer visibility indicators, and changes over time.
5. **Performance evaluation:** Measure the outcomes of implemented recommendations and use the findings to inform future actions.
6. **Automated reporting:** Generate recurring reports with evidence, priorities, unresolved issues, and recommended next steps.

## 1.3 Design principles

- Domain-first onboarding.
- Reusable tools shared across agents.
- Deterministic processing wherever possible.
- LLM reasoning only where it adds value.
- Explicit workflow state and recoverable execution.
- Idempotent operations and bounded retries.
- Evidence-backed recommendations.
- Historical tracking of all relevant measurements.
- Human approval for consequential website changes.
- Graceful handling of unavailable data sources.
- Observable, testable, and maintainable production code.

# 2. Scope and Non-Goals

## 2.1 In scope

- Website discovery and crawling.
- Technical SEO audits.
- Page speed and performance measurements.
- Search Console integration.
- Keyword opportunity analysis.
- Trend discovery.
- Competitor content analysis using permitted data sources.
- Content gap analysis.
- Content brief generation.
- AEO readiness evaluation.
- Sampled AI-answer citation monitoring.
- Historical metric comparison.
- Scheduled execution.
- Recommendation tracking.
- Report generation.
- Failure recovery and operational monitoring.

## 2.2 Out of scope for the initial release

- Unrestricted automatic publishing of content.
- Guaranteed Google ranking improvements.
- Guaranteed citations in AI-generated answers.
- Circumventing CAPTCHAs, authentication, rate limits, or access restrictions.
- Building a proprietary global search-volume database.
- Replacing a full commercial SEO data provider.
- Autonomous modification of DNS, hosting, robots directives, or other high-impact site configuration.
- Automatically purchasing backlinks or creating large volumes of low-quality content.

These capabilities should not be introduced implicitly through agent decisions. They require explicit product, legal, operational, and quality decisions.

# 3. High-Level Architecture

## 3.1 Component overview

The system consists of the following layers.

### Layer 1: Entry point and API

Responsibilities:
- Accept a website domain.
- Validate the domain.
- Create an onboarding record.
- Trigger an initial audit.
- Return job status and report references.

Technology:
- FastAPI.
- Pydantic.
- PostgreSQL.

### Layer 2: Orchestration

Responsibilities:
- Plan the workflow.
- Schedule dependent tasks.
- Invoke specialized agents.
- Manage shared workflow state.
- Handle conditional branches and failures.
- Persist execution checkpoints.
- Pause for approval where required.
- Resume interrupted work.

Technology:
- LangGraph.
- PostgreSQL-backed checkpointing.
- Redis for selected coordination and caching functions.

### Layer 3: Specialized agents

The proposed design contains four specialized agents:

1. SEO Audit Agent.
2. Keyword and Trend Research Agent.
3. Content Strategy Agent.
4. Performance and Reporting Agent.

The orchestrator coordinates these agents. It is not counted as a fifth specialized analysis agent.

### Layer 4: Shared tool registry

Responsibilities:
- Expose reusable, typed tools.
- Validate tool inputs and outputs.
- Enforce access and execution limits.
- Normalize responses from external services.
- Record execution status and provenance.

Examples:
- Website crawler.
- Lighthouse runner.
- Search Console client.
- Trend data collector.
- Keyword analyzer.
- Content evaluator.
- Report generator.

### Layer 5: Persistence and retrieval

**PostgreSQL**
- Structured business data.
- Crawl inventories.
- Audit findings.
- Keyword metrics.
- Recommendations.
- Historical measurements.
- Job records.
- Audit logs.
- LangGraph checkpoints.

**ChromaDB**
- Page-content embeddings.
- Semantic content retrieval.
- Similar-page detection.
- Topic and content similarity.
- Retrieval of relevant historical content for analysis.

**Redis**
- Cache of suitable repeatable lookups.
- Rate-limit counters.
- Short-lived coordination state.
- Optional background-job coordination.
- Optional deduplication locks with carefully designed expiry and recovery.

Redis must not be the only durable record of a job, audit, recommendation, or workflow.

### Layer 6: External data sources

- Google Search Console API.
- Lighthouse.
- CrUX and PageSpeed Insights where appropriate.
- Google Trends or another validated trend data source.
- Publicly accessible competitor pages.
- Approved keyword research providers where needed.
- Selected AI-answer engines for sampled visibility monitoring.

### Layer 7: Reporting and monitoring

- HTML report generation.
- Optional PDF exports.
- Operational logs and metrics.
- Scheduled summaries.
- Alerts for failures and significant regressions.

# 4. Agent Architecture

## 4.1 Orchestrator

### Goal

Coordinate the complete website analysis and optimization workflow from domain onboarding to recurring reporting.

### Responsibilities

1. Validate the initial domain.
2. Load website configuration and available integrations.
3. Create or retrieve the appropriate workflow record.
4. Determine which tasks need to run.
5. Invoke the SEO Audit Agent.
6. Invoke the Keyword and Trend Research Agent when required inputs are available.
7. Invoke the Content Strategy Agent after crawl and keyword data have been collected.
8. Invoke the Performance and Reporting Agent to consolidate findings.
9. Persist workflow outputs and recommendation states.
10. Pause when approval is required.
11. Resume from checkpoints after interruption.
12. Produce a final workflow status.

### Inputs

- Website domain.
- Website configuration.
- Available credentials and integration permissions.
- Previous audit references.
- Requested execution type: initial, scheduled, or targeted audit.

### Outputs

- Workflow execution record.
- Agent execution results.
- Consolidated report reference.
- Failed or skipped task list.
- Next scheduled execution information.

### Production requirements

- Explicit graph state.
- Bounded execution steps.
- Persistent checkpoints.
- Task-level timeouts.
- Retry policies.
- Idempotent side effects.
- Traceable tool invocations.
- Cancellation support.
- No direct unrestricted database access from the LLM.

### Limitations

The orchestrator cannot guarantee that every external data source will be available. It must continue with the capabilities that remain available and explicitly mark incomplete analysis.

It should not invent missing data or force an agent to return a positive recommendation when the evidence is insufficient.

### Retry behavior

The orchestrator should retry failed, retryable nodes according to their individual policies.

It should not restart the entire workflow when only one independent task fails.

If a workflow exceeds its retry budget, it should mark the affected task as failed, preserve successful results, and continue where dependencies permit.

## 4.2 Agent 1: SEO Audit Agent

### Goal

Discover the website's technical and performance issues and establish a reliable baseline for subsequent optimization.

### Responsibilities

1. Discover URLs from sitemaps and internal links.
2. Respect configured crawl scope and rate limits.
3. Retrieve public page content.
4. Identify redirects and broken links.
5. Inspect titles, descriptions, headings, canonical tags, and indexability directives.
6. Check robots.txt and sitemap accessibility.
7. Detect common duplicate or near-duplicate content patterns.
8. Evaluate structured-data presence and parsing.
9. Run Lighthouse audits against selected pages.
10. Retrieve available field-performance data.
11. Store findings and measurements.
12. Compare findings with the previous audit.
13. Assign severity and recommend next actions.

### Tools

- `discover_site_urls`
- `crawl_website`
- `inspect_page_metadata`
- `check_internal_links`
- `check_indexability`
- `inspect_structured_data`
- `analyze_page_speed`
- `get_field_performance`
- `compare_audit_results`

### Inputs

- Website domain.
- Crawl configuration.
- Sitemap and URL discovery results.
- Previous audit data.
- Performance test limits.

### Outputs

- URL inventory.
- Page-level metadata.
- Technical SEO findings.
- Performance measurements.
- Crawl errors.
- Historical change summary.

### Recommended libraries

- `httpx`
- `BeautifulSoup`
- `advertools`
- `lxml`
- `playwright`, when browser rendering is needed
- Lighthouse CLI
- Pydantic

A dedicated crawler can be added if its functionality or scalability justifies operating another component.

### Production requirements

- Configurable crawl depth and page limits.
- Per-domain concurrency limits.
- Request timeouts.
- URL normalization.
- Duplicate URL detection.
- HTML and response-size limits.
- Robots and access-policy handling.
- Safe handling of redirects.
- Separate lab and field performance measurements.
- Reproducible audit configuration.
- Source URL and timestamp on every finding.

### Limitations

- JavaScript-heavy websites may require browser rendering.
- Crawlers may miss orphaned pages that are not discoverable through accessible links or sitemaps.
- A Lighthouse score is not equivalent to real-user performance.
- A page that is crawlable is not necessarily indexed.
- Structured data does not guarantee rich results or AI citations.
- Large websites require sampling, prioritization, and crawl budgets.

### Retry behavior

- Retry temporary network errors and selected server errors.
- Respect `Retry-After` when supplied.
- Use bounded exponential backoff with jitter.
- Do not retry permanent HTTP errors indefinitely.
- Do not repeatedly fetch a page that is consistently inaccessible.
- Record failed URLs separately so successful pages remain usable.
- Resume large crawls from persisted URL worklists rather than restarting the whole crawl.

## 4.3 Agent 2: Keyword and Trend Research Agent

### Goal

Discover relevant keywords and topics with potential to improve organic visibility and attract qualified traffic.

### Responsibilities

1. Retrieve available Search Console data.
2. Identify queries already generating impressions and clicks.
3. Find queries with promising impressions but relatively low CTR.
4. Identify pages with declining visibility.
5. Discover rising and seasonal topics.
6. Generate related keyword candidates.
7. Assess search intent and domain relevance.
8. Retrieve competitor information where a suitable source exists.
9. Distinguish observed metrics from estimates.
10. Score opportunities using an explicit, versioned ranking formula.
11. Store keyword history and evidence.

### Tools

- `get_search_performance`
- `discover_trending_topics`
- `generate_keyword_candidates`
- `analyze_search_intent`
- `get_keyword_metrics`
- `analyze_competitor_content`
- `score_keyword_opportunities`

### Inputs

- Website URL inventory.
- Search Console query and page data, when authorized.
- Historical keyword metrics.
- Trend observations.
- Existing content topics.
- Optional competitor and keyword-provider data.

### Outputs

- Keyword opportunity records.
- Trending-topic candidates.
- Search-intent classifications.
- Evidence and data-source references.
- Opportunity scores and confidence levels.
- Data-quality warnings.

### Recommended libraries and integrations

- Google Search Console API client.
- `pandas`.
- `httpx`.
- Pydantic.
- A validated trend data integration.
- An optional keyword research provider.

### Opportunity scoring

A first version should use an explainable scoring model.

Potential factors:

- Domain and audience relevance.
- Existing impressions and clicks.
- CTR opportunity.
- Ranking trend.
- Trend momentum.
- Content gap severity.
- Search intent alignment.
- Competitive difficulty, when reliable data is available.
- Business value.
- Estimated implementation effort.

The scoring formula must be versioned, documented, and tested against historical recommendations.

A keyword should not receive a high score solely because a trend signal is rising.

### Production requirements

- Preserve original query and source data.
- Record measurement windows and retrieval timestamps.
- Distinguish missing data from zero.
- Deduplicate keyword candidates.
- Normalize keyword and page identifiers.
- Track geographical and device dimensions where available.
- Record provider limitations.
- Avoid unsupported precision in estimates.
- Prevent unrelated trending topics from entering the content plan.

### Limitations

- Search Console data is limited to the verified property and available reporting dimensions.
- Search Console average position is not a universal, fixed rank for every user.
- Search volume and difficulty may require third-party sources.
- Trend indices are relative and should not be interpreted as absolute search volumes.
- Trending interest does not guarantee future traffic.
- Competitor visibility may be incomplete.
- Search Console reporting can be delayed or incomplete for recent periods.

### Retry behavior

- Retry transient API and network errors with bounded backoff.
- Respect provider quotas.
- Cache suitable historical responses.
- Do not treat quota failures as evidence that a keyword has no demand.
- Do not fabricate replacement metrics.
- Mark unavailable integrations and continue with other valid sources.
- Avoid rerunning a successful historical data collection unless a refresh is required.

## 4.4 Agent 3: Content Strategy Agent

### Goal

Convert technical, keyword, trend, and existing-content evidence into a prioritized, actionable content improvement plan.

### Responsibilities

1. Match keyword opportunities to existing pages.
2. Retrieve semantically similar pages from ChromaDB.
3. Detect likely overlap between proposed and existing content.
4. Identify missing or insufficient topic coverage.
5. Recommend page updates when existing content is a suitable target.
6. Recommend new pages when a genuine content gap exists.
7. Generate content briefs.
8. Recommend titles, headings, supporting questions, and internal links.
9. Suggest relevant structured-data types where appropriate.
10. Evaluate content for factual support, clarity, relevance, and completeness.
11. Explain why each recommendation should be considered.
12. Provide measurable success criteria.

### Tools

- `retrieve_similar_pages`
- `analyze_content_gaps`
- `map_keywords_to_pages`
- `detect_topic_overlap`
- `recommend_page_update`
- `generate_content_brief`
- `evaluate_content_quality`
- `validate_structured_data_proposal`

### Inputs

- Crawl inventory and extracted content.
- Keyword opportunity records.
- Trend evidence.
- Technical audit findings.
- Historical recommendations.
- Semantic retrieval results.
- Brand guidelines, if provided.

### Outputs

Each recommendation should include:

- Recommendation ID.
- Website and target URL, if applicable.
- Target keyword or topic.
- Action type: update, create, consolidate, or investigate.
- Supporting evidence.
- Search intent.
- Proposed title and content outline.
- Relevant questions and subtopics.
- Suggested internal links.
- Expected opportunity.
- Confidence.
- Estimated effort.
- Priority.
- Validation checklist.
- Recommended measurement window.

### Recommended libraries

- ChromaDB client.
- An embedding model or embedding API.
- Pydantic.
- Python content-processing utilities.
- The selected LLM provider.
- PostgreSQL for recommendation records.

### Production requirements

- Every recommendation must reference supporting evidence.
- Content must be relevant to the domain's actual subject matter.
- Similarity alone must not determine whether two pages are duplicates.
- Existing page URLs should be preferred when updating them satisfies the same search intent.
- New content recommendations must be checked against the current content inventory.
- Factual claims must be validated against appropriate sources.
- Drafts must be distinguishable from published content.
- Content changes must be versioned.
- Publishing must require explicit authorization.

### Limitations

- Semantic similarity does not establish search intent equivalence.
- The LLM may produce incorrect or generic content.
- Keyword overlap does not necessarily imply cannibalization.
- Search intent and competitive conditions can change.
- A high-quality content brief does not guarantee ranking improvements.
- AEO recommendations cannot guarantee inclusion in AI answers.

### Retry behavior

- Retry transient model-provider and embedding-service errors.
- Validate structured outputs before persistence.
- If output validation fails, retry with a constrained correction prompt within a bounded limit.
- If content quality remains below the acceptance threshold, mark the recommendation for review.
- Do not silently convert a failed content-generation request into a successful recommendation.
- Cache embeddings using stable content hashes and model-version identifiers.

## 4.5 Agent 4: Performance and Reporting Agent

### Goal

Track SEO and AEO indicators, evaluate changes over time, and generate reliable reports that help prioritize subsequent actions.

### Responsibilities

1. Retrieve current measurements.
2. Compare them with appropriate historical baselines.
3. Identify material increases and decreases.
4. Track recommendation implementation status.
5. Link changes to their affected pages and keywords.
6. Detect predefined technical or performance regressions.
7. Track sampled AI-answer citations for selected queries and engines.
8. Distinguish correlation from demonstrated causation.
9. Generate weekly and monthly reports.
10. Recommend follow-up investigations.
11. Track unresolved recommendations.
12. Maintain a record of what was measured and when.

### Tools

- `get_historical_metrics`
- `compare_performance_periods`
- `detect_regressions`
- `track_recommendation_status`
- `measure_ai_answer_visibility`
- `evaluate_recommendation_outcomes`
- `generate_report`
- `publish_report`
- `create_alert`

### Inputs

- Current audit results.
- Search performance metrics.
- Historical data.
- Trend observations.
- Recommendation records.
- Implementation timestamps.
- Optional AI-answer monitoring observations.

### Outputs

- Weekly performance report.
- Monthly growth report.
- Technical regression alerts.
- Recommendation outcome records.
- Next-action shortlist.
- Data coverage and quality summary.

### Recommended libraries

- `pandas`.
- PostgreSQL client or SQLAlchemy.
- Pydantic.
- HTML report templates.
- Optional PDF generation libraries.
- Structured logging and monitoring tools.

### Production requirements

- Metrics must retain their original source and measurement window.
- Comparisons must use compatible dates and dimensions.
- Missing data must not be represented as zero.
- Small sample sizes must be disclosed.
- Reports must distinguish observed measurements from estimates.
- Recommendation status changes must be auditable.
- AI visibility measurements must record the engine, query, timestamp, and observation method.
- Every report must identify incomplete data sources.

### Limitations

- Search performance varies with seasonality, demand, competition, and algorithm changes.
- AI-generated answers can vary across runs, users, locations, and time.
- A citation observed for one query does not establish general AI visibility.
- Before-and-after comparisons alone do not prove causation.
- Reliable causal evaluation may require controlled experiments or suitable comparison pages.

### Retry behavior

- Retry transient database, API, and report-rendering failures.
- Use persisted report inputs to avoid unnecessarily rerunning all upstream agents.
- Never send a report as complete if required data or sections are missing.
- If optional data is unavailable, produce a clearly marked partial report when policy permits.
- Avoid sending duplicate notifications by using an idempotent report-delivery key.

# 5. Shared Tool Registry

## 5.1 Design

All tools should be reusable functions or service interfaces independent of the agent that invokes them.

Agents should not contain duplicated implementations of crawling, API authentication, retry logic, or database persistence.

The tool registry should provide:

- Typed input schemas.
- Typed output schemas.
- Authentication and authorization checks.
- Timeouts and resource limits.
- Rate-limit enforcement.
- Structured errors.
- Retry classification.
- Logging and execution metadata.
- Idempotency where applicable.
- Test doubles for integration testing.

# 6. LangGraph Workflow Design

## 6.1 Initial onboarding workflow

When a user submits a domain:

1. Validate the domain and permitted crawl scope.
2. Create a website record.
3. Determine which integrations are configured.
4. Discover robots.txt and sitemap locations.
5. Build the initial URL inventory.
6. Execute the SEO Audit Agent.
7. Collect Search Console data if authorized.
8. Collect trend observations from configured sources.
9. Execute the Keyword and Trend Research Agent.
10. Build semantic representations of eligible page content.
11. Execute the Content Strategy Agent.
12. Persist findings and recommendations.
13. Execute the Performance and Reporting Agent.
14. Generate the baseline report.
15. Schedule subsequent runs according to the configured policy.

The system should not fail the entire workflow because Search Console credentials are missing. It should report which analyses were completed and which require additional access.

## 6.2 Recurring monitoring workflow

A scheduled run should:

1. Load the website configuration.
2. Identify due tasks.
3. Check whether a compatible recent result can be reused.
4. Collect fresh data for due tasks.
5. Compare current results with historical records.
6. Recalculate keyword opportunities.
7. Update content recommendations.
8. Evaluate previously implemented recommendations.
9. Generate the report.
10. Send alerts when configured conditions are met.
11. Persist execution status and schedule the next run.

Avoid repeating a complete crawl, every Lighthouse audit, and every external API request merely because one report needs to be regenerated.

## 6.3 Conditional execution

Examples:

- If no accessible pages are discovered, stop content analysis and report the crawl failure.
- If Search Console is unavailable, continue with technical auditing and other configured sources.
- If no reliable trend data is available, mark trend analysis as unavailable rather than fabricate trends.
- If a page has an active content recommendation, avoid generating a duplicate recommendation without reassessing its status.
- If an upstream task fails, skip only dependent tasks.
- If a report is incomplete, label it accordingly.
- If approval is required, pause the relevant workflow and resume only after the approval state is recorded.

## 6.4 Workflow state

Maintain a versioned state model containing:

- Website ID.
- Run ID.
- Workflow type.
- Execution configuration.
- Task statuses.
- References to persisted results.
- Errors and warnings.
- Retry counts.
- Approval status.
- Report status.
- Completion summary.

Large crawl datasets and page content should not be placed wholesale in LangGraph state. Store them in PostgreSQL, ChromaDB, or artifact storage and reference them by ID.

# 7. Database Design

## 7.1 PostgreSQL: Source of truth

PostgreSQL should store authoritative structured records.

Proposed tables:

| Table | Purpose |
|---|---|
| `websites` | Domain configuration and website identity |
| `integrations` | Integration configuration and authorization metadata |
| `crawl_runs` | Crawl execution history |
| `pages` | Normalized page inventory |
| `page_snapshots` | Historical page metadata and content hashes |
| `technical_findings` | Audit findings and severity |
| `performance_measurements` | Lighthouse and field-performance measurements |
| `search_query_metrics` | Search Console query and page observations |
| `keyword_candidates` | Normalized keyword records |
| `keyword_measurements` | Historical keyword metrics and trend observations |
| `content_recommendations` | Proposed content changes |
| `recommendation_evidence` | Evidence supporting each recommendation |
| `recommendation_events` | Approval, implementation, and evaluation history |
| `ai_visibility_observations` | Sampled AI-answer citation observations |
| `scheduled_jobs` | Durable scheduled-work metadata |
| `job_runs` | Execution and task statuses |
| `reports` | Report metadata and artifact references |
| `tool_execution_logs` | Tool execution records |
| `audit_logs` | Important system and user actions |

The initial schema may be simplified, but ownership, timestamps, source provenance, and historical measurement requirements should be preserved.

## 7.2 Data integrity

- Use UUID primary keys where appropriate.
- Add foreign-key constraints.
- Enforce uniqueness for natural identifiers such as normalized page URLs within a website.
- Use indexes for common website, date, URL, and keyword queries.
- Use transactions for logically related database updates.
- Use migrations for schema changes.
- Apply retention policies to large historical datasets.
- Preserve recommendation history rather than overwriting previous decisions.

## 7.3 ChromaDB: Semantic retrieval

Use ChromaDB for content representations and semantic retrieval.

Potential collection:
- `website_page_chunks_v1`

Recommended metadata:
- `website_id`
- `page_id`
- `canonical_url`
- `content_hash`
- `content_version`
- `chunk_index`
- `language`
- `embedding_model_version`
- `indexed_at`

Use it to:
- Retrieve related pages.
- Find possible topic overlap.
- Compare proposed topics against existing content.
- Retrieve relevant content for recommendation generation.

ChromaDB is not the authoritative source for page metadata, recommendation status, or historical performance. Those belong in PostgreSQL.

### Vector-index lifecycle

1. Extract eligible page content.
2. Normalize the content.
3. Generate a content hash.
4. Compare the hash with the previous indexed version.
5. Skip unchanged content.
6. Generate embeddings for changed content.
7. Update the corresponding ChromaDB records.
8. Record the index version and completion status.

Do not assume that a successful PostgreSQL transaction also guarantees a successful ChromaDB update. These are separate systems. Use an idempotent indexing job and a reconciliation process to recover from partial failures.

## 7.4 Redis: Cache and coordination

Potential use cases:
- Cache selected external API responses.
- Enforce request quotas.
- Cache reusable configuration.
- Coordinate background tasks.
- Prevent duplicate work using bounded locks.
- Maintain short-lived progress or notification state.

Redis should not be the only storage location for:
- Workflow checkpoints.
- Audit history.
- Recommendations.
- Reports.
- Durable job definitions.

### Cache correctness

Cache keys must include the relevant website, query parameters, data source, and version information.

Cache expiry should reflect data freshness. Search metrics, trend data, and crawl results have different refresh requirements.

Invalidate or bypass caches when a forced refresh is requested.

# 8. Scheduling and Background Execution

## 8.1 Scheduling requirements

The system needs recurring tasks, not just an API endpoint that launches an agent.

The scheduler must support:
- Initial audits.
- Recurring crawls.
- Search performance collection.
- Trend discovery.
- Keyword analysis.
- Content opportunity generation.
- Weekly and monthly reports.
- Retry scheduling.
- Job cancellation and status tracking.

## 8.2 Proposed implementation

For the first production version, use a scheduler that creates durable job records in PostgreSQL and dispatches work to background workers.

Redis can coordinate worker activity, but PostgreSQL should preserve the authoritative job state.

A candidate scheduling library is Prefect. A simpler scheduler can be used initially if the operational requirements remain modest.

The scheduler and LangGraph serve different purposes:
- The scheduler decides **when** a workflow should run.
- LangGraph controls **how** the workflow executes.

Avoid implementing competing schedules independently inside each agent.

## 8.3 Suggested frequencies

| Task | Initial schedule |
|---|---|
| Technical crawl | Weekly |
| Lighthouse checks | Weekly for priority pages |
| Search performance collection | Daily where useful |
| Trend discovery | Daily or several times per week |
| Keyword opportunity analysis | Weekly |
| Content strategy analysis | Weekly |
| Consolidated report | Weekly |
| Broader growth review | Monthly |

These are initial defaults. Actual frequencies should depend on website size, data freshness, external quotas, and processing cost.

# 9. Retry, Timeout, and Failure-Recovery Policy

Retries must be implemented at the appropriate tool or workflow-node boundary.

## 9.1 Error classification

### Transient failures

Examples:
- Connection reset.
- Temporary DNS or network failure.
- HTTP 429.
- Selected HTTP 5xx responses.
- Temporary database connection failure.
- Temporary model-provider unavailability.

Action:
- Retry with bounded exponential backoff and jitter.
- Respect `Retry-After`.
- Enforce a maximum attempt count and overall deadline.

### Permanent failures

Examples:
- Invalid input.
- Unsupported URL scheme.
- Missing required permission.
- Persistent HTTP 404.
- Invalid API credentials.
- Unsupported configuration.

Action:
- Do not retry indefinitely.
- Record the error.
- Mark the task failed or blocked.
- Continue independent workflow branches where possible.

### Data-quality failures

Examples:
- Malformed provider response.
- Unexpected schema.
- Missing required fields.
- Invalid metrics.
- Unparseable model output.

Action:
- Validate the response.
- Retry only if the failure may be recoverable.
- Quarantine invalid records when appropriate.
- Do not persist invalid measurements as successful results.

## 9.2 Initial retry defaults

These values are starting defaults, not universal settings.

| Operation | Initial maximum attempts | Example timeout policy |
|---|---:|---|
| Single-page HTTP fetch | 3 | 15–30 seconds |
| External API request | 3 | 30–60 seconds |
| Lighthouse audit | 2 | 120–180 seconds |
| Embedding request | 3 | Provider-dependent |
| LLM generation | 2–3 | Provider-dependent |
| Database transaction | 3 for transient failures | Connection and query timeouts |
| Report rendering | 2 | Based on report size |

Timeouts should be configurable per operation.

For large crawls, apply per-page timeouts and a separate total workflow deadline.

## 9.3 Idempotency

Retrying a task must not create duplicate recommendations, measurements, reports, or notifications.

Use:
- Stable job IDs.
- Idempotency keys for side effects.
- Unique constraints where appropriate.
- Content hashes.
- Persisted task status.
- Transactional updates.
- Explicit delivery state.

For report generation, reuse the same report-run identity during retries.

For external publishing or notification, distinguish between generating a report and successfully delivering it.

## 9.4 Checkpoint and recovery behavior

- Persist LangGraph checkpoints in PostgreSQL.
- Store tool outputs before moving dependent workflow steps forward.
- Resume from successful checkpoints when possible.
- Avoid rerunning expensive independent tasks unnecessarily.
- Reconcile incomplete ChromaDB indexing.
- Record exhausted retries.
- Provide a controlled mechanism to rerun failed tasks.

Checkpointing does not automatically make every external side effect safe. Tool operations must still be designed for idempotency.

# 10. Keyword Opportunity Scoring

The system should provide an explainable prioritization mechanism rather than asking an LLM to assign arbitrary scores.

## 10.1 Candidate factors

- Relevance to the website.
- Existing impressions and clicks.
- CTR opportunity.
- Search visibility trend.
- Topic trend momentum.
- Search intent.
- Existing content coverage.
- Competition, when reliable data exists.
- Business relevance.
- Estimated implementation effort.

## 10.2 Scoring model

A normalized weighted score can be used:

`Opportunity Score = Σ(weight_i × normalized_signal_i)`

Each factor should be normalized to a defined range. Weights should be configurable and versioned.

Missing values must not automatically be treated as zero. The scoring model should handle missing signals explicitly and reduce confidence where appropriate.

The agent should expose the component scores and supporting evidence.

## 10.3 Recommendation categories

1. **Optimize existing page:** The topic is relevant, and an existing page is a suitable target.
2. **Create new content:** A meaningful topic gap exists.
3. **Expand a content cluster:** Related pages exist but important subtopics are missing.
4. **Investigate declining visibility:** Performance has decreased and requires diagnosis.
5. **Monitor emerging trend:** Interest appears to be increasing, but evidence is not yet sufficient to justify content investment.
6. **Deprioritize:** The topic is irrelevant, redundant, low-confidence, or poorly aligned with the website's goals.

The system should avoid generating a new page when improving an existing page is the better choice.

# 11. AEO Evaluation and AI Visibility

AEO should be treated as a set of measurable content and visibility checks, not a guaranteed ranking score.

## 11.1 Content readiness checks

Evaluate:
- Directness of answers.
- Clarity of definitions.
- Relevance to user questions.
- Factual support.
- Source attribution.
- Logical headings.
- Useful structured data.
- Internal discoverability.
- Accessibility to permitted crawlers.

## 11.2 AI-answer visibility monitoring

For a defined set of questions:
1. Record the query.
2. Record the target answer engine.
3. Run the permitted observation method.
4. Capture the response and cited sources where available.
5. Determine whether the domain or target page appears.
6. Store the timestamp and method.
7. Repeat observations under documented conditions.
8. Report citation frequency and its limitations.

Do not assume that every AI platform offers a public API for answer monitoring. Do not treat a single observation as proof of general visibility.

## 11.3 AEO limitations

- AI answers can vary between runs.
- Citation availability differs across providers.
- Results can vary by location, language, personalization, and time.
- A page can be accessible without being cited.
- Schema markup does not guarantee AI citation.
- AEO readiness scores are internal evaluation metrics unless validated against an appropriate outcome dataset.

# 12. Security and Access Controls

## 12.1 Domain validation

The initial input is a website domain, but the crawler must not become an unrestricted network-fetching service.

Controls should include:
- Allow only supported HTTP and HTTPS schemes.
- Validate and normalize the target domain.
- Restrict crawling to the configured site scope.
- Revalidate redirect destinations.
- Block loopback, private, link-local, and other prohibited IP ranges.
- Protect against DNS rebinding and server-side request forgery.
- Apply response-size and request-time limits.
- Avoid following arbitrary links to internal infrastructure.
- Enforce crawl concurrency and rate limits.

These controls are especially important if the agent will be exposed to users other than its operator.

## 12.2 Credentials

- Store credentials in a secret manager or secure environment configuration.
- Never place secrets in LLM prompts, logs, ChromaDB, or report content.
- Request only the permissions required for each integration.
- Support credential rotation and revocation.
- Use read-only access wherever possible.
- Clearly report when credentials are missing or expired.

## 12.3 Website modifications

The initial release should be read-only and recommendation-focused.

Later implementation capabilities should require:
- Explicit authorization.
- A preview or diff.
- Validation.
- An approval record.
- A rollback or recovery plan where feasible.
- Post-change verification.

The LLM must not directly execute arbitrary shell commands or unrestricted website modifications.

## 12.4 Data privacy

- Store only the page content and operational data required for the intended analysis.
- Define retention policies.
- Separate websites and their data by tenant.
- Enforce authorization in both SQL queries and semantic retrieval.
- Prevent cross-website retrieval.
- Redact sensitive information from logs.
- Record important access and change events.

# 13. Testing Strategy

Testing should be performed at multiple levels.

## 13.1 Unit tests

Test deterministic functions independently.

Examples:
- URL normalization.
- Keyword normalization.
- Opportunity scoring.
- Retry classification.
- HTML metadata extraction.
- Content hashing.
- Report calculations.
- Idempotency-key generation.

## 13.2 Tool integration tests

Use controlled test sites and mocked external APIs.

Verify:
- Correct HTTP behavior.
- Data-source error handling.
- Response validation.
- Rate-limit behavior.
- Retry policies.
- Output schemas.
- Persistence behavior.

## 13.3 Agent evaluation tests

Create a benchmark dataset with known answers and expected actions.

Examples:
- A page missing a title.
- A broken internal link.
- A page with poor measured performance.
- A high-impression query with low CTR.
- A trending but irrelevant topic.
- A new topic with no suitable existing page.
- Two similar pages targeting different search intents.
- A recommendation that should be rejected for lack of evidence.

Measure precision, recall, recommendation relevance, evidence quality, and false-positive rates.

## 13.4 End-to-end tests

Run the complete workflow against a controlled test domain.

Verify:
- URL discovery.
- Technical audit generation.
- Keyword analysis.
- Content recommendation generation.
- Database persistence.
- Checkpoint recovery.
- Report generation.
- Partial failure behavior.

## 13.5 Failure-injection tests

Simulate:
- HTTP 429 and 5xx responses.
- API credential failures.
- Timeouts.
- PostgreSQL interruptions.
- Redis unavailability.
- ChromaDB indexing failures.
- Malformed model responses.
- Worker termination during a crawl.
- Duplicate scheduler triggers.
- Failure during report delivery.

The workflow should preserve completed work, avoid duplicate side effects, and accurately record incomplete tasks.

## 13.6 Initial acceptance targets

These targets must be validated against a representative test dataset before being adopted as production requirements.

| Metric | Initial target |
|---|---:|
| Recall for predefined technical issues | ≥95% |
| Precision for reported technical issues | ≥95% |
| URL discovery coverage on a known test site | ≥95% |
| Accuracy of reported source metrics | ≥95% agreement within defined tolerances |
| Precision of top 20 keyword recommendations | ≥80% against an expert-reviewed benchmark |
| Correct mapping of recommendations to an existing page or justified new-content opportunity | ≥90% |
| Scheduled run completion | ≥95%, excluding documented external outages |

Traffic growth is not an initial engineering acceptance criterion. It should be measured as a real-world business outcome after the system has established a reliable baseline.

# 20. Open Questions and Decisions Required

These questions remain open. They should be resolved before the architecture is frozen.

## A. Website and onboarding

1. **Website platform:** Is the site built on WordPress, Shopify, a custom framework, or another platform?
2. **Website ownership:** Will the system analyze only websites you own or manage, or should it support arbitrary public domains?
3. **Website scale:** What is the expected range of URLs per website?
4. **Multiple websites:** Is this a single-domain tool initially, or should the architecture support multiple websites and users from the beginning?

## B. Search and keyword data

5. **Google Search Console:** Can users authorize the system to access their Search Console property?
6. **Keyword data:** Is a completely open-source and free stack mandatory, or are optional commercial data integrations acceptable?
7. **Competitor analysis:** Should competitor analysis be limited to public page content, or should optional keyword and backlink data providers be supported?
8. **Trend sources:** Which countries, languages, and markets should the system initially cover?

## C. AI model and agent behavior

9. **LLM provider:** Should the system support hosted APIs, local models, or both?
10. **Agent autonomy:** Should the first release generate recommendations only, or should it eventually apply approved website changes?
11. **Content generation:** Should the system generate complete drafts or only outlines and content briefs?
12. **AEO scope:** Which AI-answer engines should be monitored in the first release?

## D. Infrastructure

13. **Deployment environment:** Local server, AWS, Azure, Google Cloud, or another environment?
14. **ChromaDB deployment:** Embedded local persistence or a separately operated ChromaDB service?
15. **Scheduling:** Is a lightweight scheduler sufficient, or do you expect high-volume concurrent jobs requiring a more substantial workflow platform?
16. **Scale and concurrency:** How many websites and simultaneous audit jobs should the initial system support?

## E. Reporting and evaluation

17. **Report delivery:** Should reports be available through an API and dashboard, or also delivered by email or another channel?
18. **Evaluation window:** How long should the system wait before assessing whether an implemented content recommendation appears to have helped?
19. **Business outcomes:** Is the primary target organic traffic, qualified leads, conversions, AI-answer citations, or a combination?
20. **Acceptance criteria:** Should the proposed engineering thresholds be retained as initial targets, or should we establish them after running a benchmark?

## 21. Recommended Next Step

Before implementation, resolve the highest-impact open questions first:

1. Website platform and expected website size.
2. Whether Search Console access is available.
3. Whether commercial keyword data sources are allowed.
4. Preferred LLM deployment model.
5. Initial deployment environment.
6. Whether the first release is recommendation-only or approval-gated for changes.

These decisions affect integration design, security, deployment, and testing. The remaining choices can be refined during implementation without changing the fundamental architecture.

**Proposed baseline:** Start with a single modular application, four specialized agents, LangGraph orchestration, shared typed tools, PostgreSQL, ChromaDB, Redis, and durable scheduled workflows. Keep website changes approval-gated, measure every recommendation against evidence, and scale infrastructure only when actual workload and reliability requirements justify it.
